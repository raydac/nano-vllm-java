## 1. Implementation Progress
- Tornado plan-cache records (`ConvKey`, `PlanKey`, `WeightKey`, `TornadoDecoder.Key`) use the generated record `equals` and `hashCode`. A `float[]` component is still an identity key. CausalLM records keep an identity `equals` so two loaded graphs are not walked field by field. `GroupKey` stays a class: each lookup builds a new `float[][]`, and equality is identity of the inner buffers.
- `Conv2d` packs a single-group filter (patch ≥ 16, at least 8 outputs) and multiplies it with `MatmulRuntime.linear`, so Vector GEMV covers YOLO's wide 1×1 and 3×3 layers. Depthwise and smaller filters stay on the direct loop. When TornadoVM is the selected backend, every convolution — including depthwise — runs as a device kernel on the NCHW picture: weights stay resident (`FIRST_EXECUTION`) and SiLU is fused into that task, so the nine-times-larger packed window is not uploaded. `YoloConv` asks for that fused SiLU. CPU backends still apply SiLU on the thread pool. Semantic and classification heads pass the engine runtime instead of forcing one thread.
- `Conv1d` and `ConvTranspose1d` gather a single-group filter into rows and multiply it with `MatmulRuntime.linear`, so Whisper's stem and Piper's vocoder use the same Vector or Tornado GEMM as chat. Depthwise 1-D filters stay a per-channel loop and use the Vector API along time when that module is loaded. A short depthwise layer stays on the calling thread; a long one joins the pool. Other shapes still split output channels. A Whisper-sized 512→512 stride-2 layer dropped from about 7.6 s in the scalar loop to about 170 ms on one thread and about 80 ms on all cores. A Piper-sized dense layer dropped from about 5.1 s to about 120 ms / 70 ms. Whisper attention of 32 keys or more is one matmul per head, and those heads run together. A dense softmax row uses SIMD. Control-token suppression reads the vocabulary piece instead of decoding every id.
- `TranscribeHelloWorld` and `SynthesizeHelloWorld` call `allCpuThreads()` and print `loaded in` plus `decoded in` or `synthesized in`, with the processor count on the load line. A clip shorter than 30 s is still zero-padded to 30 s: a shorter mel made whisper-base emit nothing or mishear “World”. On this i7-8550U, `piper-hello.wav` through whisper-base prints “Hello, World.” in about 7 s of decode. Five seconds was not reached.

## 2. Architecture & Technical Discoveries
- Module `com.igormaznitsa.nanollvm` exports `models`, `llm`, `chat`, `rag`, `jev`, `exceptions`, `tokenizer`, `utils`. Hidden: `engine`, `layers`, `tensor` (and `.kernels` / `.scalar` / `.tornado` / `.vector`), `internal`, `prompts`, `models.internal` (and `.audio` / `.fasttext` / `.yolo`), `models.llmcontainer`, `models.llmarch`. No `java.desktop` require: pictures are `ArgbImage` (row-major `0xAARRGGBB`). Sound in and out is a `byte[]` WAV (`LlmInSound` / `LlmOutSoundData`); the library does not open `javax.sound`. `YoloStreetHelloWorld.fromBufferedImage` / `toBufferedImage` are the AWT boundary. The weather sample's `SoundClip` and `VoiceReplyHelloWorld` are the mixer boundary. `requires static` for `jdk.incubator.vector`, `tornado.api`, `tornado.clblast`. No `opens`, `uses`, or `provides`. `tornado.runtime` stays off the descriptor; the Tornado launcher puts it on the module path. `ModuleExportsTest` locks the descriptor, the package set, and public signatures.
- `Conv2d` uses packed GEMV when `groups == 1`, the patch is at least 16 floats, and there are at least 8 outputs. One picture reuses one patch buffer and one row buffer (`Conv2d.reusingPatches`); both are removed from the calling thread when the picture returns, including on throw. A convolution outside that scope allocates for that call only. Depthwise stays a direct channel loop. Numeric difference versus the scalar loop is the same GEMV tolerance as chat (about 1 ulp per dot). `MatmulRuntime.linear` splits outputs only when there are at least 128 of them, so a YOLO nano map (16–64 channels) stayed on one core. Tall maps now split by input rows (`MIN_PARALLEL_ROWS` 32). Chat prefill still splits the wide output. A full detect forward stayed near 1 thread because `YoloAttention.attendHead` and `YoloMath.silu` were serial (profile: attention and SiLU each about a fifth of the samples, next to GEMV). Attention now packs each head and uses `MatmulRuntime.linear`; SiLU splits the activation across the same pool. The 3×3 gather copies an interior window with no per-pixel bounds check. Real YOLO26n detect, 800×544: about 780 ms on 1 thread and about 470 ms on 8 threads. The gap stays under 2× because GEMV and the gather share one memory bus.
- YOLO26 weights are ONNX initializers only (`Yolo26Loader`), bound onto `Yolo26Model`. Stem channels pick the scale: 16 n, 32 s, 64 m or l, 96 x. A `model.2.m.1` weight selects l over m. Medium and larger set `c3k` on the early `C3k2` stages. Class-tower width is `max(P3 channels, min(classes, 100))`. Detection uses the one-to-one head (`one2one_cv2` / `one2one_cv3`). Rank cap, score floor, letterbox edge, pose-joint floor, and label cap come from `LlmInImage` (defaults 300, 0.25, 640, 0.5, 5). A knob that does not apply to the head is rejected when it is not the default. No NMS and no `.pt` pickle. A segment mask is `coeff · proto` inside that detection's box (proto is 160×160 on a 640 letterbox). The outline is the clockwise contour of the largest component there. Sorting every mask edge by angle draws lines across the picture. Pose is Pose26. Tower width and keypoint channels are the weight's leading axis (synthetic tests still use the published nano 85 / 51). Class count is that same axis on the class tensor, not 80 / 19 / 1000. Decode is `(value + cell center) × stride`. A joint below the caller's confidence is omitted; the index is the model's, and `Keypoint.COUNT` is only the COCO skeleton a sample may draw. Sigma weights in the ONNX are training-only and are not loaded. Object hits store the class index only. `LlmModel.classNames()` is `classes.txt` beside the ONNX file, loaded once. The loader does not pick COCO, DOTA, Cityscapes, ImageNet, or `person`. Depth returns an empty name list.
- Tool calling is local `ModelTool` functions, not MCP. The dialect follows the checkpoint: Qwen3 Hermes JSON, Qwen3.5 XML function/parameter (the 0.8B template, same family as the `qwen3_coder` parser), LFM2 Pythonic tokens, Gemma 4 `call:`/`response:` with `<|"|>` strings. The chat loop parses the raw decode (special tokens kept), runs the function, and appends the result before the next generate.
- Activation buffers: `ActivationWorkspace` is bound for a transformer step and removed in `finishStep`, including when `bindStep` or the forward throws. The freelist stays on the transformer (cap 128M floats), not on the thread. Each causal forward keeps the tensors the next layer still needs and parks the rest (length ≥ 256) for reuse. `TornadoDecoder`'s open group is the other thread local: `closeFrame` removes it before flush. Neither is inherited by pool workers. `prefillLogits` detaches the returned logits so the freelist cannot overwrite them. `Sequence.pagedSlots` grows one slot index per sequence; `Context` publishes it once per step. `Sampler` selects top-k with an `int` heap. Nucleus sampling pops that same order until the cumulative mass reaches top-p, instead of mergesorting the vocabulary.
- Zero-length `byte[]`, `int[]`, `float[]`, and `float[][]` are the shared `EmptyArrays` constants. `Tensor.zeros` with `numel == 0` returns that `float[]`. Tornado's no-bias sentinel is its own one-element array: TornadoVM 8 requires every kernel array to be transferred, and a zero-length buffer is not a device argument.
- A Tornado device task cannot call `System.arraycopy`. It is a native method, so the compiler bails out with TC-E1003 ("has no bytecode"). The unrotated RoPE tail in `ropeHeads` is an element loop.
- Speed review (inference hot path): multi-token `gemvRows` walks an 8-row weight panel across every token before the next panel (scalar and Vector). Decode (`rows == 1`) stays one GEMV. A JevHelloWorld hotspot export (`jevhotspot.csv`) was 86% CPU in `ScalarFloatKernels.gemvPanel8` — that JVM had no Vector API (`--add-modules jdk.incubator.vector`); IntelliJ does not load `.mvn/jvm.config`. On this i7-8550U (AVX2, 8 lanes), vector panel-across-tokens was ~12× the profiled scalar per-token GEMV on a 96×640×4096 prefill. TornadoVM mode runs GEMV (including one token), attention (including one query), and elementwise kernels on the device. Decode matmul is one launch (`prefersSingleShotGemv`). One-token GEMV uses the device kernel; CLBlast stays multi-token only (SGEMV returned NaN on POCL). RMSNorm is one device task for every row, not one launch per head. Attention history stays on the device and a later step copies only the new token. Gated DeltaNet stays on the CPU. UHD 620 does not beat AVX2 on single-token F32 GEMV, so a Tornado chat can be slower than Vector and that measurement is the device.

- Qwen3.5 text is architecture `qwen3_5`, not an alias of `qwen3`. Full-attention layers use leading partial RoPE (text-only; MRoPE collapses when positions match). Linear layers keep conv + recurrent state in `DeltaNetStateArena`, cleared with the existing conv-state hook. HF names `model.language_model.*` and root `language_model.*` (Jeff checkpoint) both canonicalize to `model.*`. The same peel covers `text_model`, `base_model.model`, and a repeated `model.model`. Packed Q/K/V and gate/up merge only when the schema does not already name that tensor, and only as a whole path segment. A second copy or a matrix that is not config `[out, in]` (or that layout swapped) fails the load. `q_proj` stays unfused (query | gate). Gemma 4 QAT uses the same name peel and rejects a duplicate tensor.
- `RMSNorm.forward` walks `numel / lastDim` rows, so a `[tokens, heads, headDim]` tensor matches the old reshape-to-2d-then-back path.
- `HfConfig` compact constructor freezes a null `ropeScaling` to an empty map, so `WeightLayers.ropeTheta` can call `containsKey` directly.
- `IntStream.toList()` is already unmodifiable; `List.copyOf` around it was an extra copy.
- Public `LLM.generate` / `generateTokenIds` overloads stay: they are the caller-facing surface.
- TornadoVM Maven coordinate is `8.1.0-jdk22plus`. The installed SDK here is OpenCL 8.1.0 (`TORNADOVM_HOME=/home/igorm/SDK/tornadovm-opencl`). Optional `tornado-clblast` is compile-only.
- TornadoVM 8.1.0 does not speed this OpenCL path. `withDynamicShapes()` is the CUDA TC compiler (compile-once across sizes; their steady-state GPT-2 time was unchanged, and the OpenCL driver has no hook). `consumeFromUnifiedMemory` is Metal, needs a Tornado native array in `Arena.ofAuto()`, and `OCLTornadoDevice` keeps the default `isUnifiedMemorySupported() == false` — Java `float[]` weights cannot use it; CUDA reports the same false because HMM was slower than a copy. `bindCUDADeviceBuffer` is CUDA-only and throws on OpenCL. `initializeDeviceAsync` hides about 70 ms of context setup and does not compile kernels; `TornadoAvailability` already touches the runtime before the first graph. The on-demand copy-back fix applies to `UNDER_DEMAND`, which these graphs do not use. Decode stays limited by F32 GEMV bandwidth and launch count on the iGPU.
- Multi-token dense GEMV uses CLBlast SGEMM when `libclblast` runs. One-token GEMV never reaches CLBlast (SGEMV returned NaN on POCL) and uses the device kernel from TornadoVM's `MatrixVectorRowMajor` example: one workgroup of 128 lanes per output row, coalesced weight reads, 4 accumulators, local reduction. One thread per row was the slow shape (their example measured about 10× slower than the workgroup kernel). A non-finite CLBlast result or a failed launch drops CLBlast for the rest of the process. `-Dnanollvm.tornado.clblast=false` keeps the multi-token kernel. The weight slice is copied once into a Tornado `FloatArray`. Weights and the bias sentinel stay resident (`FIRST_EXECUTION`) for one token count. A change of token count closes those plans first: prefill and decode would otherwise each keep a device copy, and the second copy of Qwen3-0.6B `gate_up` (24 MB) overflows the 4 GB `tornado.device.memory` heap. A GEMV whose weight span exceeds the device budget is streamed through one reused tile (`EVERY_EXECUTION`). On the default 4 GB `tornado.device.memory` heap that budget is 32 MiB, which is why the Qwen3-0.6B LM head (~593 MB) streams. Bytes above 4 GiB, still capped by the device's global memory and max allocation, can hold that matrix instead. Pinning it beside the layer graphs overran the default 4 GB heap (Qwen3-0.6B bench 0.15 tok/s). KernelContext plans attach the worker grid before execution and do not precompile without it. One task graph for every layer of a forward was slower than a short group (Qwen3-0.6B, 64 tokens, 0.11 tok/s) and is not used. Qwen3 dense layers do not use that per-call GEMV: a task graph (default four layers, `-Dnanollvm.tornado.layers`) runs norm, QKV, RoPE, paged attention, and the MLP, and prefill walks it one token at a time so the weights are not uploaded again. The activation between those tasks stays on the device. Llama, Gemma 3, Gemma 4, Qwen3 (fused or separate projections, including packed weights expanded once), Qwen3.5 full attention, and LFM2 attention use that same layer graph. Gemma 4 QAT is dequantized once and the SRQ scales stay in the graph. A shared-KV Gemma 4 layer re-reads the producer cache from the host each token. Qwen3.5 Gated DeltaNet recurrence and LFM2 short convolution stay on the CPU; their MLP is still one device graph. Chat attention, including a single decode query, is one task graph: an append of the new token, then the score. The resident cache is `FIRST_EXECUTION`; a replaced cache is refreshed with `transferToDevice`. A failed attention launch fails the step. cuDNN packed-QKV attention is CUDA-only and does not match causal grouped-query attention with a sliding window.
- OpenCL devices outside the sandbox: `0:0` Intel UHD Graphics 620 (Tornado default), `0:1` POCL CPU. A sandboxed `tornado --devices` sees only POCL. `etc/tornado.backend` is OpenCL only. The CUDA driver jar can still abort startup when `libcuda` is missing, so the TornadoVM bench child passes `-Dtornado.enabled.backends=OpenCL`. `libclblast.so.1` is on the SDK `lib` path.
- `KernelChatBench` child JVMs must use the context class loader URLs. Under `mvn exec:java`, `java.class.path` is Maven's classpath. The TornadoVM child must be started with the `tornado` command (`tornado.exe` on Windows): the Maven parent never loads the SDK, so a parent device probe skips TornadoVM even when `tornado --devices` lists both OpenCL devices. The extensionless `bin/tornado` in the Windows SDK is a shell script; CreateProcess error 193 is that file. The `windows` Maven profile sets `tornado.launcher` to `tornado.exe`. When `TORNADOVM_HOME` is set, profile `tornadovm-home` points `tornado.executable` at `$TORNADOVM_HOME/bin/<launcher>`. `KernelChatBench` already resolves PATH then `TORNADOVM_HOME/bin`.

## 3. Technical Debt & Refactoring
- GGUF IQ tables, Tornado kernels, and espeak dictionaries are data or numeric kernels. Do not “compact” them into shared abstractions.
- Java causal graphs still repeat decoder-layer shape. Tornado uses one shared layer graph; Gated DeltaNet and LFM2 short conv remain CPU steps in front of that graph's MLP.
- `LLM` still has many one-line generate overloads. They exist so callers do not pass unused flags.

A space inside a called name is removed before lookup (`os_ name` matches `os_name`); Qwen3-0.6B emits that split for `os_name`. Llama and Gemma 3 fail at build. MCP is not the engine protocol. At most four executions per user message. Raw `generate` does not run tools.
- Speed work stays algorithmic. Nucleus sampling keeps a heap prefix instead of sorting the vocabulary. Vector GEMV stays one 8-row panel on `SPECIES_PREFERRED`. Splitting that panel onto `SPECIES_256` / a 2-row kernel was a JDK 27 inliner trick: the 2-row form measured slower (about 8 tok/s vs 11 tok/s on the same 4×16×8 Qwen3-0.6B smoke) and still spent most samples in the lane fallback.
- KernelChatBench Qwen3-0.6B, 46 prompt + 256 completion, after streaming the vocabulary matrix and before layer grouping: scalar 5.35 tok/s, Vector 9.17 (1.71×), TornadoVM 1.50 (0.28×, 170 s). The pinned-vocabulary run was 0.15 tok/s. First use compiles one program per group of four layers. UHD 620 single-token F32 GEMV stays slower than AVX2. Grouping is device-tested (five layers match one-at-a-time) and not re-benched.
- `Bench` Maven profile `bench` forks the timed generate under async-profiler 4.6. `package` and `exec:exec@bench` must be the same invocation, or the classpath is an older installed snapshot. Reports: `nano-vllm-java-samples/target/bench-profile/`.
- Activation reuse, paged slot cache, and primitive top-k select are in. `CoreUnitTest` covers zeroed buffer reuse, detached logits, and append-only slot growth. Prefill GEMV reuses an 8-row weight panel across tokens (`batchedGemvMatchesPerTokenGemv`). Scalar batched and per-token GEMV stay bit-identical. The Vector path can differ by about 1 ulp when the panel is inlined into the row loop versus the single-token loop (Windows, `S_256_BIT`: `0.984` vs `0.9839999`); that assertion allows `1e-5`. Tornado one-token matmul and one-query attention run on the device (`oneTokenMatmulAndOneQueryAttentionRunOnTheDevice`). Re-profile `JevHelloWorld` with `--add-modules jdk.incubator.vector` so a Vector run's hotspot is `VectorFloatKernels`, not scalar.

- `KernelChatBench` on Windows resolves `tornado.exe` from `PATH` or `TORNADOVM_HOME/bin`, and the `windows` Maven profile sets `tornado.executable` to `tornado.exe`. Worker `--classpath` / `--params` are shell-quoted because TornadoVM pastes them into `os.system`/`cmd.exe`: unquoted `;` truncates the classpath (NoClassDefFoundError for library classes), and Unix single quotes break `Path.of`. The tornado child also drops `CLASSPATH` so the launcher cannot append it with a Unix `:`. Default model is `requireKernelChatBench()` (Qwen3-0.6B → Gemma3 → Jeff → Gemma4 → SmolLM2); compact ONNX prints a note that Tornado ratios are launch-bound.
- `JevLevel` javadoc now states RAW vs L0 (rotations, eight-state prior, ordered scores stay one prefill) and includes a two-engine usage example. `require` and `Builder.jevLevel` point at it.
- Russian checkers records (`Sq`, `Move`, `Played`, `Choice`, `Step`, `Hop`) have javadoc for the short components: file/rank axes, path vs captured vs crowned `result`, forced single-move turns, and a hop's land/victim.
- Board a–h axis is `Sq.column` (0 = a). `Step` uses `columnDelta` and `rankDelta`. Screen position in the rotated drawing is `across`, not `column`.
- Jeff's checkers prompt does not ask for a written plan. Jev reads the next letter and the chat template closes an empty think block. `positionText` lists pieces; `choiceLabel` notes captures, promotion, a win, or `landing taken at once`. The question states that preference order.
- Russian checkers sample is in (`RussianCheckersHelloWorld`). Rules covered by `RussianCheckersHelloWorldTest` (no model load). A live game still needs `models/Jeff-Qwen3.5-0.8B`. That run is `assets/russian_checkers_03nov26.gif` in `README.md`, under the checkers controls.

## 5. Known Issues & Limitations
- On `images/yolo-street.jpg`, YOLO26n detect scores the closest dark car about 0.81. YOLO26n seg scores that same car about 0.013. The sample keeps it because the box covers more than 2% of the picture. A flat cutoff of 0.01 without the size check also keeps dozens of edge fragments.
- Weather place is the city of the public network address (often the ISP), not a street address. The lookup sends that address to ipwho.is / geojs / ipapi.co, then the coordinates to Open-Meteo.
- Tool calls are chat-only (`chat` / `chatOnce`). Llama and Gemma 3 fail at `build()` if a tool is registered: there is no Llama 3 header template here, and Gemma 3 has no tool-call tokens. Gemma 3's pythonic prompt convention is not wired.
- Qwen3.5 support is text-only safetensors. Vision inputs, LoRA adapters, Qwen3-Next, and Qwen3.5 MoE stay rejected. GGUF is not a load path for `qwen3_5`.
- Tornado kernel tests skip when no Tornado device is on the module path. Maven Surefire does not launch the `tornado` CLI, so those tests skip there. A YOLO26n detect on this UHD 620 takes about 3.6 s through the device convolution, against about 470 ms on 8 CPU threads. The device path is used only when TornadoVM is the selected kernel backend.

## 6. Open Questions & Pending Decisions
- TornadoVM 8.1.0 was checked against the OpenCL layer graphs (6 Nov 2026). No API from that release is worth wiring in for tok/s. Two local gaps remain: prefill calls the layer graph once per token, so each weight is reread per prompt token even though `gemvTiled` already has a token index; decode GEMV uses a 128-lane local reduction on a short dot product. Qwen3-0.6B on this UHD 620 was 1.50 tok/s against 9.17 for Vector. The shared DDR4 bus is on the order of 20 tok/s if every FP32 weight byte moved once, so a better kernel can raise Tornado and the Vector path stays the fast decode on this chip.

## 8. User Advice and Recommendations
- Prefer the standard JDK methods whenever they express the same thing: `Objects` (`hash`, `equals`, `requireNonNull`), `Arrays` (`hashCode`, `equals`, `copyOf`, `mismatch`), `Math` (`clamp`, `min`, `max`, `fma`), and the other `java.util` / `java.lang` helpers. Compact standard code has priority over a hand-rolled loop or a local `31 * hash + …` mix. Keep a custom form only when the JDK method does a different job: content hash versus identity hash, `Objects.hash(this)` on a type whose `hashCode` is identity, or a numeric kernel where the helper would allocate or hide the arithmetic.
- The library stays generic. A checkpoint's labels, class count, pose width, mel-band count, language-token set, letterbox size, score floors, detection cap, label cap, and tool-call cap come from the file or from the caller. Do not add a COCO / ImageNet / Cityscapes / Whisper-language table, a sample photo policy, a greeting, or a published-checkpoint constant on a path the user can set. Samples may hardcode a demo (street classes, COCO limbs, "Hello, World."); the library must not.
- Architecture of a supported family stays in the library: YOLO26 block graph and the n/s/m/l/x stem table, letterbox gray 114, Whisper 16 kHz / n_fft 400 / hop 160 / 30 s pad, tool-call token dialects, Jev's decision instruction. Those are the algorithm, not a sample. A file whose stem is not 16/32/64/96 is still refused. Depth's log clamp (−4..5) and the 30 s pad (not `max_source_positions`) are the remaining family constants.
- `LlmInImage.builder` sets image size (multiple of 32, default 640), min probability (0.25), max detections (300), keypoint confidence (0.5), and max labels (5). `addClass(name, floor)` overrides the score for one class name. A knob that does not apply to the loaded head is rejected when it differs from the default. Class count and pose width are the weight's leading axis. `Keypoint.COUNT` is only the COCO skeleton a sample may draw.
- `LLM.Builder.maxToolExecutions` defaults to 4. `ChatSession.unusableHistoryText` is empty unless the caller sets it. Whisper mel bands follow `num_mel_bins`. Auto language uses tokenizer pieces `<|xx|>` of 2–3 letters.
- README commands use `mvn`. Do not put local launcher names (`mvn22`), machine paths, or bench-profile property recipes in `README.md`.
- Keep public generate overloads. Compact internals, not the caller API.
- Optimize algorithms in Java. Do not shape kernels around the current JVM's inliner or Vector API intrinsification; that changes between JDKs.
